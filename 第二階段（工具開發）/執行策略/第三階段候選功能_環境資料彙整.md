# 第三階段候選功能備忘：環境資料彙整與物件比對

> 建立日期：2026-04-17
> 狀態：**候選功能，現階段不動工**
> 目的：記錄構想，待第二階段三大工具上線並累積名單後，再評估是否納入第三階段

---

## 一、原始構想

使用者輸入「工作地點」＋「有興趣的物件（一個或兩個）」，系統彙整並視覺化呈現：

- 通勤時間（開車／大眾運輸／騎車）
- 採購動線（超市、市場、量販距離）
- 親子設施（學校、公園、托嬰、醫療院所）
- 環境資料（空品、噪音、淹水風險等）
- 雙物件比較模式

---

## 二、現階段不做的三個理由

### 2.1 定位錯位

擇居的差異化是「幫你想清楚要不要買、買了會不會後悔」——反思型工具。三個核心工具都是**往內看**：認識自己（性格）、檢視進度（地圖）、面對代價（財務）。

這個功能是**往外看**：外部環境資料的聚合、視覺化、比對。這條賽道已被 591、樂屋網、Google Maps、樂居、實價登錄衍生工具佔滿，且他們在資料更新頻率、API 預算、工程人力上都比擇居強幾個量級。

擇居的優勢不在「誰資料最全」，而在「誰能讓猶豫的人冷靜下來」。一旦跨進資料聚合賽道，就是拿自己的弱項打對手的強項。

### 2.2 技術成本跳一個層級

現階段技術棧為純前端 HTML/CSS/JS + Vercel 靜態部署，三大工具 MVP 難度 1～2.5/5 都在可承受範圍。

這個功能至少需要：

- Google Maps Platform（Distance Matrix API、Places API、Directions API）
- 環境資料來源（環保署空品 API、學校 POI、醫療院所 POI、災害潛勢圖資）
- 地理空間運算與快取層
- 後端 serverless function 或 API gateway

保守估 MVP 難度 4/5，且每次使用者查詢都會產生 API 成本。在名單還沒開始累積、付費轉換模型尚未驗證的階段，押這個成本不划算。

### 2.3 時機不對

目前路線圖：**我的決策性格 → 我的買房地圖 → 我的財務診斷**，三個工具都還沒完全上線。應先把這三件事做完、累積 LINE 名單、驗證付費轉換，再考慮擴張。這個功能再有價值，插隊只會稀釋注意力。

---

## 三、值得保留的變體：輕量嵌入模組

不要做成獨立工具，而是作為「我的買房地圖」**第 8～12 步（看屋、評估區域）的輕量嵌入模組**：

**產品設計原則：**

1. 只在已經走到看屋階段的使用者才觸發
2. 輸入工作地點 + 候選物件（最多兩個）
3. 只回傳三個最關鍵指標：
   - 通勤分鐘數（大眾運輸為主）
   - 所在都會圈層級（雙北／桃竹／中部／南部）
   - 生活機能分數（三級制：充足／普通／需依賴外部）
4. 不做重型視覺化，用擇居現有的卡片風格三行呈現
5. 文案語氣維持冷靜同行者：「你走到這一步了，該檢查這幾件事」

**技術設計原則：**

- 一次性 serverless function 呼叫，不做即時動態地圖
- 結果快取 30 天（同地址短期內不重複計算）
- 免費額度 API 優先（Google Maps 每月 $200 credit、環保署公開 API）
- 付費層級設計：免費版只能查一個物件，付費會員才能雙物件比較

---

## 四、啟動條件（判斷何時可以動工）

**不滿足以下條件前，不要動這個功能：**

1. 三大工具（決策性格、買房地圖、財務診斷）全部上線滿三個月
2. LINE 名單累積達 3,000 人以上
3. 財務診斷付費轉換率驗證 ≥ 5%
4. 有明確的使用者回饋指出「需要比較不同物件的通勤與生活機能」（從 LINE 私訊、問卷、或客服回饋中統計）
5. 工程資源有餘裕（不影響三大工具迭代優化）

## 五、競品現況速記（供未來評估用）

| 平台 | 環境資料覆蓋度 | 視覺化 | 雙物件比較 | 擇居差異化空間 |
| --- | --- | --- | --- | --- |
| 591 | 高 | 中 | 無 | 缺決策框架 |
| 樂居 | 中 | 高（實價地圖） | 部分 | 缺主觀判斷輔助 |
| Google Maps | 高（通勤、POI） | 高 | 無 | 無整合購屋情境 |
| 實價登錄衍生工具 | 中（偏價格） | 中 | 無 | 缺生活面向 |

**擇居若要進場，差異化必須是「情境化詮釋」而非「資料更多」**——例如：
「你是風險規避型人格（來自工具一），這個物件通勤 45 分鐘，會比你想像中更消耗你的穩定感。」

把**工具一的人格結果**當作環境資料的詮釋框架，這才是擇居能做、別人不能做的事。
