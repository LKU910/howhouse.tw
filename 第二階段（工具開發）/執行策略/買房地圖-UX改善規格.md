# 買房地圖（progress.html）UX 改善規格

> 本文件基於 Dcard 用戶回饋 + 現有程式碼分析，供實作頻道直接參照修改。
> 對應檔案：`第二階段（工具開發）/deploy/progress.html`

---

## 一、核心問題：首次進入不知道要幹嘛

**來源：** Dcard B1 回饋 —「買房地圖的操作對我來說好像不是很直觀，剛進去的時候不知道自己要幹嘛」

**現狀分析：**

用戶第一次進到 progress.html 時看到的是：

1. 標題「我的買房地圖」+ 副標「看看你走到 18 步的哪了。不急，按自己的節奏走。」
2. 一個 quiz CTA（如果沒做過測驗）或 persona banner（如果做過）
3. 三個 summary chip 全部顯示 0 / 0 / 18
4. 七個收合的 phase section（只有 in-progress 的會展開，但新用戶全部都是 not_started，所以全部收合）

**問題：** 新用戶看到的是一面「關著的門」— 七個收合的階段、三個都是零的數字。沒有任何視覺引導告訴他「點開第一個來看看」或「從這裡開始」。

---

## 二、改善項目

### 改善 A：新用戶引導（Onboarding State）

**目標：** 第一次進入時，讓用戶在 3 秒內知道「這個工具是做什麼的、我下一步要做什麼」。

**實作規格：**

1. **偵測新用戶條件：** `state.steps` 所有 18 步的 `status` 都是 `not_started`（即 countClear === 0 && countThinking === 0）

2. **新用戶首次進入時：**
   - 自動展開第一個 phase（`自我準備`），讓用戶直接看到 Step 01 和 Step 02 的卡片
   - 在 pathMap 最上方插入一段引導文字區塊（class: `onboarding-hint`），內容建議：
     ```
     從第一步開始就好。
     點開任何一步，把你現在的狀態標記起來。想到什麼就寫在筆記裡，之後回來看會很有用。
     ```
   - 這段引導在用戶「對任一步驟做出第一次狀態改變」後自動隱藏（加一個 `localStorage` flag 如 `zeju-progress-onboarded`）

3. **視覺樣式：** 引導區塊用淡底色（如 `background: #FDF6EE`，即現有的 bronze 淡色），圓角卡片，字體大小 14px，不要太突出但要可見。

**修改位置：**
- `renderPath()` 函式（約第 821 行）：在 `PHASES.forEach` 之前，判斷是否為新用戶，若是則插入引導區塊
- `render()` 初始化時：新用戶自動呼叫 `togglePhase('prep')` 展開第一階段
- `setStatus()` 函式（約第 926 行）：在狀態改變時檢查是否為首次操作，若是則隱藏引導

---

### 改善 B：Summary Chips 增加直覺性

**目標：** 讓頂部三個數字不只是「統計」，而是能引導行動。

**現狀：** 三個 chip 分別顯示「想清楚了 / 正在想 / 還沒走到」的數量，純數字呈現。

**實作規格：**

1. **加入進度條：** 在 summary 區塊下方新增一條細長的進度條（progress bar），高度 4px，圓角，三色分段：
   - 綠色 `#6B8E6B`（想清楚了的比例）
   - 金色 `#8A6820`（正在想的比例）
   - 灰色 `#E5E2DE`（還沒走到的比例）
   - 寬度按比例計算：各狀態數量 / 18

2. **進度條下方文字：** 一行小字顯示完成比例，例如「3/18 步已確認」，`font-size: 12px; color: #999`

**修改位置：**
- `renderSummary()` 函式（約第 743 行）：在更新數字後，額外渲染 progress bar
- HTML 結構：在 `#overallSummary` div 之後新增一個 `progress-bar-wrapper` div
- CSS：新增 `.progress-bar` 相關樣式

---

### 改善 C：步驟卡片的操作可發現性

**目標：** 讓用戶更容易理解每張卡片的三個按鈕是什麼、該怎麼用。

**現狀：** 每張 step-card 底部有三個 status-btn：「尚未面對 / 正在想 / 想清楚了」。按鈕文字偏抽象，用戶可能不清楚點了會怎樣。

**實作規格：**

1. **按鈕文字微調：**
   - 「尚未面對」→「還沒開始」（更口語、更直覺）
   - 「正在想」→ 維持不變（已經夠清楚）
   - 「想清楚了」→ 維持不變

2. **首張未操作卡片的按鈕加上微動畫：** 對於新用戶看到的第一張卡片（Step 01），如果從未被操作過，三個按鈕輕微 pulse 動畫（`@keyframes subtle-pulse`，opacity 在 0.7–1 之間循環，週期 2s），吸引注意力。用戶點擊任一按鈕後動畫停止。

**修改位置：**
- `renderPath()` 中的 step card 按鈕文字（約第 886–891 行）：改 `尚未面對` 為 `還沒開始`
- `setStatus()` 函式中的按鈕 index mapping（約第 948 行）：確認 mapping 不受影響（因為是用 index 而非文字）
- CSS：新增 `@keyframes subtle-pulse` 和條件 class `.pulse-hint`

---

### 改善 D：「展開全部」按鈕位置與功能

**目標：** 降低用戶不知道可以展開的問題。

**現狀：** 「展開全部」是 fixed 在底部 toolbar 的按鈕。新用戶可能沒注意到，或不知道上面的七個 phase 是可以點開的。

**實作規格：**

1. **在 pathMap 上方加一個小型文字提示：** 在第一個 phase-section 之前加一行 `font-size: 12px; color: #AAA`：「點擊任一階段即可展開」。這行文字在用戶手動展開過任何 phase 之後隱藏。

2. **底部 toolbar 「展開全部」改為 toggle：** 目前的 `expandAll()` 只能展開，建議改為展開/收合 toggle：
   - 文字切換：「展開全部 ↔ 收合全部」
   - 點擊展開全部後文字變成「收合全部」，再點則全部收合

**修改位置：**
- `expandAll()` 函式：改為 toggle 邏輯
- toolbar HTML（約第 530 行）：按鈕文字動態切換
- `renderPath()` 開頭：插入提示文字

---

### 改善 E：鼓勵區塊的時機與位置

**目標：** 讓鼓勵訊息更有效地出現在用戶需要的時候。

**現狀：** 鼓勵區塊（`#encouragement`）在頁面最底部，新用戶需要往下捲才看得到。且新用戶狀態下的預設訊息「18 步看起來很多，但你不需要一次走完」其實很適合放在更醒目的位置。

**實作規格：**

1. **新用戶狀態下：** 將鼓勵訊息移到 summary chips 下方、pathMap 上方（或整合進改善 A 的引導區塊中）
2. **非新用戶（已有操作紀錄）：** 維持在底部即可，因為此時用戶已理解工具邏輯，底部的鼓勵是回顧性質

**修改位置：**
- `render()` 函式：根據是否為新用戶，決定 `#encouragement` 的 DOM 位置
- 或更簡單的做法：新用戶引導區塊（改善 A）本身就包含鼓勵語句，底部鼓勵區塊新用戶時隱藏

## 三、不需要改的部分

以下是目前設計中已經做得不錯、不建議動的地方：

- **三狀態設計**（還沒開始 / 正在想 / 想清楚了）：概念清楚，符合買房決策的心智模型
- **七階段分群**：將 18 步收進 7 個 phase 是正確的資訊架構決策，降低認知負擔
- **筆記功能**：在「正在想」時可寫、「想清楚了」時鎖定並顯示的機制很好
- **persona tip 整合**：根據測驗結果在特定步驟顯示個人化建議，這個做得很細
- **dependency hint**：步驟之間的關聯提示是差異化特色

## 四、實作優先序

| 優先 | 項目 | 預估工作量 | 理由 |
|------|------|-----------|------|
| 1 | 改善 A：新用戶引導 | 小 | 直接解決 B1 的核心痛點「不知道要幹嘛」 |
| 2 | 改善 B：進度條 | 小 | 增加視覺回饋，強化成就感循環 |
| 3 | 改善 C：按鈕文字與動畫 | 極小 | 低成本高效果的可發現性改善 |
| 4 | 改善 D：展開提示與 toggle | 小 | 輔助性改善 |
| 5 | 改善 E：鼓勵區塊位置 | 極小 | 可整合進改善 A 一起做 |

建議 A + C 一起做為第一批，B + D + E 為第二批。

## 五、技術備註（給實作者）

- 頁面為純前端靜態 HTML，無框架，所有邏輯在 `<script>` 區塊內
- 狀態存在 `localStorage`（key: `zeju-progress`），結構見 `defaultState()` 函式
- 有 Firebase + LINE LIFF 整合做雲端同步，但本次 UX 改善不涉及後端邏輯
- CSS 為頁面內 `<style>` 區塊，非外部 Tailwind（nav/footer 用 Tailwind，主體用自寫 CSS）
- 修改後需跑 `inject.py` 重新注入 nav/footer，但 progress.html 的主體內容不受 inject 影響
- 部署流程：改完 push 到 GitHub，Vercel 自動部署
